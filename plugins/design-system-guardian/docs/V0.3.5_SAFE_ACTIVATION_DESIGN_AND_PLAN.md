# Guardian v0.3.5 Safe Activation Design and Plan

## Outcome

Release the second independently recoverable Usage Rules Lane checkpoint.
Guardian v0.3.5 preserves every v0.3.2, v0.3.3, and v0.3.4 capability, then
adds an explicit-permission activation path, an append-only rule snapshot v2,
and deterministic Flutter enforcement for the first two provable
predicate-and-scope pairs.

The public surface remains exactly two skills:
`build-with-design-system` and `audit-design-system`.

## Hard compatibility contract

Nothing from v0.3.2, v0.3.3, or v0.3.4 may be removed, weakened, renamed, or
silently reinterpreted.

- Keep `policy/policy-v1.json` byte-identical with digest
  `3bf2913583cee2d791aed5093bc1df905b26dcdbb0c4d945f0ae5b2eddaaa99f`.
- Keep strict profile schema v1 and every existing profile byte unchanged.
- Keep snapshot schema v1, its current pointer, approval sequence records, and
  immutable history unchanged and readable.
- Keep existing run pins, audit v1/v2 inputs, audit results, post-run evidence,
  duplicate-file lineage, Figma read-back, UX/accessibility evaluation,
  sentinels, Elo v2-v4, installers, CLI commands, and exit codes.
- Keep v0.3.4 `guardian rules validate` output and exit behavior unchanged.
- Keep all six rule predicate shapes previewable.
- Keep exactly two visible skill directories.
- Add no credential store, Figma connection, background service, or runtime
  dependency.
- Do not publish company rules, identifiers, paths, prompts, designs, runtime
  evidence, or local Guardian state.

Any inherited regression blocks the release.

## Authority boundary

User permission enables the reviewed v0.3.5 evaluator. It does not approve a
rule, identity, component, token, icon, mapping, or source.

An enforceable rule must be inside a complete catalog v2 that is signed by the
already pinned external catalog authority and bound to:

- the immutable policy digest;
- the exact unchanged profile digest;
- the exact source cut and Figma allowlist;
- a fresh, complete source observation;
- the next global catalog approval sequence; and
- exact published design-system identities and exact non-inferred Flutter code
  mappings.

Ordinary prose, local names, equal-looking values, unsigned artifacts, caller
claims, and permission alone never become authority.

## Why profile and snapshot v1 are not migrated in place

The profile digest is already bound into catalog signatures, snapshots,
approval sequences, and run pins. Replacing profile v1 with profile v2 would
invalidate retained evidence. v0.3.4 also rejects unknown fields and unexpected
files in its v1 snapshot history.

Safe Activation therefore creates a parallel rule-snapshot lineage:

```text
profiles/<profile-id>/
  profile.json                    # existing v1, unchanged
  snapshots/                      # existing v1 history, unchanged
  approval-sequences/             # existing v1 history, unchanged
  current-snapshot.json           # existing v1 pointer, unchanged
  rule-snapshots/                 # new append-only schema-v2 history
  rule-approval-sequences/        # new sealed continuation records
  current-rule-snapshot.json      # new sealed v2 high-water pointer
```

When no rule namespace evidence exists, v0.3.5 behaves exactly like v0.3.4.
Once any rule namespace evidence exists, missing, partial, redirected, corrupt,
or inconsistent v2 evidence is an integrity failure; Guardian must never fall
back silently to v1.

Old v1 run pins remain readable. New runs after activation pin the effective v2
snapshot ID using the unchanged run-pin contract. A normal runtime downgrade is
unsafe after activation and must be refused by installers; restoration requires
a separately reviewed restoration workflow. Preserving v1 evidence is data
compatibility, not permission for an old runtime to ignore activated rules.

## Catalog v2 input

Catalog v1 remains accepted before activation and remains byte-for-byte
compatible. Catalog v2 is the exact catalog v1 contract plus:

```json
{
  "schemaVersion": 2,
  "rules": [],
  "ruleEvidence": {
    "captureAttempted": true,
    "sourceComplete": true
  }
}
```

The external Ed25519 catalog approval covers these fields with the complete
catalog. `sourceComplete=true` plus an empty `rules` array proves a genuinely
empty rulebook. Missing rule evidence, a v1 catalog after activation, or
incomplete capture is never treated as complete-empty.

Catalog v2 uses one global approval sequence:

- first v2 sequence = retained v1 high-water + 1;
- later v2 sequence = retained v2 high-water + 1;
- reuse, gaps, rollback, cross-profile evidence, or divergent content at one
  sequence fails closed;
- after activation, catalog v1 cannot advance production state.

A higher, externally signed catalog with incomplete or invalid rule capture
must advance to a sealed blocking v2 head when its safe identity and sequence
can be verified. Preflight then returns the applicable source/integrity blocker
instead of silently continuing with an older rulebook.

## Rule snapshot v2

`schemas/rule-activation-snapshot.schema.json` defines a strict sidecar
snapshot. It carries the complete normalized catalog evidence plus:

- `previousSnapshotId` linking the first v2 snapshot to the v1 high-water and
  later v2 snapshots to the prior v2 head;
- canonical `rules` and `rulesDigest`;
- privacy-safe validation counts and reason codes;
- rule-capture completeness evidence;
- the exact activated predicate-and-scope capability set;
- the first activation permission digest;
- the global approval sequence and external approval digest;
- an immutable `snapshotId` and local authority seal.

For v2, `catalogDigest`, `snapshotId`, the external approval, and the local
authority seal all cover the rules, provenance, and capture evidence.

## Permission flow

The CLI remains non-interactive. The skills hide mechanics and surface one
plain-language permission request.

```text
guardian rules activate preview --profile <id> --input <signed-catalog-v2.json>
guardian rules activate apply --input <permission-bound-bundle.json>
```

Preview is read-only. It verifies policy, profile, current v1 high-water,
catalog authority, source freshness/completeness, rules, identities, mappings,
and sequence continuity. It returns `permission_required` and a binding over:

- policy and profile digests;
- current v1 snapshot and catalog digests;
- candidate v2 catalog and rules digests;
- candidate approval sequence and authority key;
- schema/namespace target;
- evaluator ID; and
- the exact activated predicate-and-scope pairs.

Apply requires `granted=true`, recomputes the full binding, rejects any race or
tampering, writes one append-only v2 snapshot, and atomically advances only the
v2 pointer. Denial or mismatch performs zero writes. Exact replay is
idempotent; divergent replay fails.

After the first activation, later signed catalog v2 refreshes use
`guardian snapshot ingest` without another migration permission. Publishing a
rule in an allowlisted, externally approved source is the rule approval act;
the one-time permission only enables evaluation.

## First protected rule capabilities

Activation is bound to predicate-and-scope pairs, never only predicate names.
v0.3.5 activates exactly:

1. `forbidden_identity_in_scope` with `scope=compilation_unit`;
2. `max_instances_per_scope` with `scope=compilation_unit`.

These two reduce to deterministic counts of exact analyzer-resolved,
catalog-mapped constructor identities within one complete Dart compilation
unit.

The following remain stored and previewable but not machine-proven in v0.3.5:

- either active predicate with `scope=widget_class`;
- `forbidden_nesting`;
- `required_companion`;
- `allowed_parents`;
- `variant_context`;
- judgment rules.

They produce `not_assessed` and incomplete rule coverage (exit 4), never a
silent pass. Informative rules are surfaced as context and never gate.
Complete predicate, composition-graph, project-overlay, and judgment
attestation enforcement remains v0.3.6 scope.

## Flutter enforcement

The existing Flutter config v1 remains unchanged for v1 runs. Activated runs
receive strict Flutter config v2 with:

- rule snapshot ID and rules digest;
- active compiled predicates using exact approved code identities;
- privacy-safe inactive rule coverage metadata; and
- the existing policy, profile, source-cut, package, toolchain, and config
  digest bindings.

One analyzer rule emits `guardian_usage_rule` for deterministic violations.
The host-owned runner recognizes that diagnostic, prevents suppressions through
the existing suppression checks, and projects it into the existing component
compliance lane. A violation exits 1. Any in-scope rule not assessed by this
release keeps coverage incomplete and exits 4. No caller-written clean result
can authorize production.

The audit-result, build-plan, and run-manifest schemas do not change in v0.3.5.
The existing protected authority lane remains the final production authority.

   retaining all 25 existing schemas.

6. Implement config v2, `guardian_usage_rule`, runner projection, and audit

8. Add immutable synthetic Elo v5 achievements; keep public score genesis and
   all local score/history data outside Git.
9. Add strict SemVer no-downgrade checks to Guardian-controlled generic host

10. Update version metadata, README, changelog, and portable host manifests to
    0.3.5.
11. Run all old and new tests, schemas, validators, privacy/history, package,

## Release-blocking acceptance criteria

- No inherited file is deleted from policy, schemas, skills, adapters,
  manifests, migrations, sentinels, or tests.
- All 439 inherited core tests and all 57 Flutter tests remain green.
- v1 profile, snapshot, pointer, sequence, and existing run-pin bytes are
  identical before and after preview, denial, and successful activation.
- Preview performs zero writes; apply without exact permission performs zero
  writes.
- Valid apply creates only new v2 evidence; exact retry is idempotent;
  interrupted or divergent apply fails closed and recovers deterministically.
- Missing/corrupt v2 state never falls back to v1 after activation.
- The first v2 sequence continues the v1 high-water exactly.
- Catalog signature, snapshot ID, authority seal, catalog digest, and rules
  digest detect mutation of rule content, provenance, status, or evidence.
- Only the two approved compilation-unit predicate pairs can become active.
- Exact pass/fail boundary tests and bypass attempts are deterministic.
- Unsupported rule coverage exits 4 and never becomes green.
- v0.3.4 rule previews remain byte-for-byte behavior-compatible.
- Exactly two skills and the immutable policy digest remain unchanged.
- Public Git history contains only implementation and synthetic example data.
- All public manifests are 0.3.5 and MIT licensed.
- Windows and Ubuntu CI pass before merge, tag, release, and local host update.
