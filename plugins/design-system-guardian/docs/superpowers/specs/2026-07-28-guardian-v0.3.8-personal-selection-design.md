# Design System Guardian v0.3.8 — Personal Design-System Selection

## Problem

Guardian v0.3.7 assumes that an authorized company design-system owner supplies
an externally signed onboarding bundle. That assumption blocks the intended
primary user: an individual employee or contractor who already has legitimate
Figma access and wants Guardian to use only the design system selected for the
current task.

The plugin must not require company participation. It must ask the individual
user which accessible design-system libraries to use every time a new task or
Figma file begins, because the same user may work across companies, clients,
products, and unrelated design systems.

## Locked user experience

1. At the start of every new Guardian task or Figma file, the host uses its
   existing Figma connection to discover the current working file and candidate
   published library files. Guardian adds no Figma credential or second plugin.
2. Guardian presents every exact candidate with its display name and stable
   Figma file identity. Previous choices may be preselected only as a visual
   convenience; they are never applied without a new confirmation.
3. The user explicitly marks candidates as **Use** or **Do not use**. Several
   related files may be selected together, such as components, icons, tokens,
   and typography belonging to one design system.
4. Guardian previews the exact local operation without writing. After the user
   confirms that exact selection, Guardian stores a sealed, task-scoped
   selection and builds or refreshes a local catalog containing only the
   selected libraries.
5. Unselected libraries are forbidden even when the user can access them.
   Missing, incomplete, ambiguous, unpublished, detached, stale, or unavailable
   evidence never becomes approved.
6. The selection applies only to the exact task, current working file, candidate
   inventory, source versions, and catalog digest. A new task, another Figma
   file, a changed candidate set, or changed source evidence requires a new
   user confirmation.
7. If the user selects no design system, Guardian stops visual work. It does not
   invent, substitute, sample, or silently reuse the previous task's system.

## Architecture

### Two authority modes

Guardian supports two additive catalog-authority modes:

- `personal_local` is the default individual-user route. The user selection is
  the approval act for that exact task. On first confirmed use, Guardian creates
  its immutable policy anchor and enables a separate personal capability sealed
  by Guardian's existing host-owned snapshot authority. It does not create or
  impersonate a company/design-owner signing key.
- `external_signed` preserves the complete v0.3.2-v0.3.7 design-owner and
  enterprise route unchanged. Existing profiles, signatures, snapshots, rules,
  migrations, and release evidence remain valid.

The personal capability reuses the existing catalog sequence, snapshot sealing,
freshness, and integrity pipeline through an explicit local-HMAC attestation
variant. It does not represent company approval. It records only that the
individual user selected those exact accessible Figma sources for one task.

### Portable CLI

Add one host-neutral command group:

```text
guardian selection preview --run-id <id> --input <discovery.json>
guardian selection apply --input <permission-bound-selection.json>
guardian selection status --run-id <id>
```

- `preview` and `status` are zero-write.
- `apply` requires explicit permission bound to the policy, run, working file,
  complete candidate inventory, selected and excluded file identities, exact
  source versions, canonical catalog digest, and exact catalog read-back
  digest.
- The agent performs these commands for the user. The user never copies keys,
  hashes, profiles, catalogs, or policy files.

The discovery input is local evidence produced through the existing Figma
connection. It includes one working file, a canonical candidate list, complete
catalog data for the selected published libraries, source-completeness
evidence, and complete one-to-one `figma_plugin_api_catalog_readback` evidence
for every canonical token, component, and icon. Guardian validates exact
selected file/version, stable binding or asset identity, published status, and
locator uniqueness before showing the selection. This evidence is explicitly
`unprotected_caller_carried`, not an independent company signature.

### Stored evidence and task binding

- One sealed personal-capability record distinguishes `personal_local` from an
  existing external authority without changing the immutable policy digest.
- Personal profiles use the existing strict profile schema and contain only the
  selected library file keys plus the exact current working file.
- A sealed personal-profile binding records the selection/catalog provenance;
  external profiles have no such record and keep their old behavior.
- A sealed selection record is stored under the selected profile and run ID.
  It contains only stable identities, versions, digests, selected/excluded
  status, and permission evidence—not Figma content or user activity.
- Preflight for a personal profile requires a matching selection record for the
  same run before it may pin the snapshot. Existing external profiles continue
  through the unchanged preflight path.
- Existing enterprise run pins remain schema version 1. New personal run pins
  use schema version 2 and additionally seal the personal authority mode,
  selection digest, target Figma file, and exact selected/excluded sources.
  Version 1 remains loadable for already-created enterprise runs but can never
  satisfy a new personal selection.

### Catalog construction and enforcement

- Only published assets and complete values from selected files may enter a
  personal catalog.
- Every token, component, icon, style, variant, property, and mapping retains
- Every canonical token must have exactly one selected Figma variable/style
  binding, and every selected registry identity must have exactly one published
  file/node/asset proof. Missing, duplicate, injected, excluded, or drifted
  evidence blocks before local authority is created.
  its exact stable source identity and version.
- Guardian's host-owned authority authenticates the canonical personal catalog
  with a domain-separated HMAC and advances its append-only approval sequence;
  normal snapshot verification remains intact.
- Equal-looking values, similar names, framework defaults, inferred matches,
  wrappers, substitutions, manual recreation, and generated assets remain
  forbidden.
- Duplicate working files remain supported only through exact published-main
  component lineage. Selecting a copied file never approves detached or cloned
  definitions.
- In personal mode, complete Guardian-validated Figma read-back can expose exact
  violations but remains `not_assessed` because catalog and read-back are
  caller-carried. The result states `assuranceMode=personal_local`.
  Missing or incomplete read-back remains `not_assessed` or the exact blocking
  source status. The externally signed assurance path is not weakened.

## Privacy and release boundary

- Profiles, Figma discovery, selections, catalogs, authority keys, snapshots,
  runs, audits, prompts, product source, and local Elo history remain under
  `~/.design-system-guardian/` and never enter GitHub, plugin packages, release
  artifacts, telemetry, or public Elo cases.
- Public tests use synthetic Figma identities and content only.
- The plugin continues to expose exactly `build-with-design-system` and
  `audit-design-system`. No new plugin, skill, service, dependency, adapter, or
  credential is added.
- The immutable policy digest remains
  `3bf2913583cee2d791aed5093bc1df905b26dcdbb0c4d945f0ae5b2eddaaa99f`.

## Compatibility and migration

- No existing trust anchor, external catalog authority, profile, snapshot,
  permission, rule, judgment decision, migration, release, or Elo record is
  rewritten.
- Existing `external_signed` homes remain external and never gain personal
  capability automatically.
- A fresh personal installation is created only after an exact selection apply.
- If existing partial, incompatible, redirected, or conflicting trust evidence
  exists, personal setup stops and requests recovery.
- A profile ID is deterministically derived from the selected library identity
  set. Different clients or selected sets cannot blend; repeated identical
  selections reuse the same isolated profile.

## Required tests

- Preview is zero-write and shows every exact candidate as selected or excluded.
- Apply without permission, with changed candidates, selected files, versions,
  working file, catalog, policy, or run ID fails with zero writes.
- First personal apply atomically creates policy trust, local authority, one
  profile, one snapshot, and one task selection; retry is idempotent.
- Every new run requires another confirmation even for an identical design
  system. A prior run's permission or selection cannot be replayed.
- Multiple selected libraries pass; every unselected library and asset fails.
- Injected tokens, components, and icons without exact one-to-one catalog
  read-back fail before writes; duplicate token or asset locators cannot prove
  multiple identities.
- Empty selection blocks visual work.
- Switching client, working file, duplicate file, candidate inventory, or
  source version invalidates the selection.
- Incomplete/unavailable/stale Figma evidence remains distinct and never passes.
- Exact published duplicate-instance lineage passes; detached/cloned/local
  definitions fail.
- Existing external-signed onboarding and all v0.3.2-v0.3.7 tests remain green.
- Public privacy/history checks prove no local company or user data is included.
- Codex, Claude Code, OpenClaw, Kimi, Qwen, and generic Agent Skills expose the
  same v0.3.8 package and exactly two skills.

## Acceptance criteria

An individual user can begin a new task, see the accessible design-system
library candidates, choose exactly which libraries Guardian may use, confirm
that choice once for the task, and build/audit using only those exact sources
without company or design-owner participation. A different task or file always
asks again.

Within the cooperative personal-local flow, the host must obtain discovery and
catalog read-back from its genuine existing Figma connection and must not
author either input. Content digests must be computed from independently read
Figma values, never copied from the catalog being checked. Implementation
read-back must run the fixed shipped collector. Only an exact identity inside the selected local catalog can
receive an `allowed` local-guidance resolution, and that resolution must state
`authorityMode=personal_local`, `independentProvenance=false`, and
`productionReady=false`. Clean personal Figma or Flutter audit coverage
remains `not_assessed`. A same-account process can fabricate matching inputs
or bypass Guardian; this route never claims protection against that actor or
independent company/Figma provenance.
