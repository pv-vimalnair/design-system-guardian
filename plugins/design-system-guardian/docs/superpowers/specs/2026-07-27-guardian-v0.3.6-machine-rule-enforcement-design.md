# Guardian v0.3.6 Machine Rule Enforcement Design

## Outcome

Release one additive public Design System Guardian v0.3.6 checkpoint that
finishes deterministic Flutter enforcement for the six machine-rule predicate
shapes introduced in v0.3.4, adds honest `widget_class` scope, exposes the
effective rules through `guardian rules list`, and reports rule compliance in a
separate Usage Rules lane.

The release remains one portable public package with exactly two visible
skills:

1. `build-with-design-system`
2. `audit-design-system`

The same package remains usable from Codex, Claude Code, OpenClaw, terminal and
generic Agent Skills hosts, Qwen Code, Kimi Code, and any compatible host that
can invoke the portable `guardian` CLI. Host-specific manifests and launchers
are adapters to the same core; they do not create separate Guardian products.

## Non-negotiable compatibility contract

Nothing shipped in v0.3.2, v0.3.3, v0.3.4, or v0.3.5 may be removed, weakened,
renamed, or silently reinterpreted.

### Keep

- Keep `policy/policy-v1.json` byte-identical with digest
  `3bf2913583cee2d791aed5093bc1df905b26dcdbb0c4d945f0ae5b2eddaaa99f`.
- Keep exact-identity-only selection, deny-wins precedence, source freshness,
  duplicate-file lineage, binding/read-back, diagnostic sentinels, UX and
  accessibility evaluation, manifests, audits, self-checks, weighted Elo,
  migrations, installers, exit codes, and privacy boundaries.
- Keep all v1 profile, catalog, snapshot, approval-sequence, run-pin, rule,
  activation, Flutter-config, audit, and evolution evidence readable.
- Keep the v0.3.5 evaluator and its two approved compilation-unit capabilities
  exactly as authorized by the v0.3.5 permission.
- Keep `guardian rules validate` and `guardian rules activate` compatible.
- Keep exactly two visible skill directories and no background service,
  credential store, extra Figma connection, or new runtime dependency.

### Add

- An explicitly permissioned `guardian-flutter-usage-rules-v2` evaluator.
- Deterministic support for all six existing machine predicates.
- Deterministic `widget_class` scope for the two scoped predicates.
- `guardian rules list` as a zero-write canonical inventory.
- An additive `usageRulesLane` in new audit evidence and readable reports.
- Executable inheritance tests spanning the public v0.3.2-v0.3.5 contracts.
- Zero-write generic installation status and a clear Windows
  `host_restart_required` recovery result.

### Remove

Nothing.

### Defer to v0.3.7

- Machine authorization of judgment-rule attestations.
- Project-specific tighten-only overlays.
- Protected remote/WORM release-head infrastructure.
- New framework adapters, services, dependencies, skills, or Figma plugins.

The deferment is an explicit roadmap split to reduce release risk. Judgment
rules remain `not_assessed`; they do not become passes. Informative rules remain
non-gating context as defined in v0.3.4. Project overlays cannot weaken or
replace company rules because v0.3.6 does not load them at all.

## Trust and privacy boundary

The authority order remains:

```text
immutable policy -> evaluator contract -> company profile -> signed catalog
```

Deny always wins. A rule can govern production only when its exact identities,
variants, mappings, source evidence, rule snapshot, and evaluator permission
are all valid. Names, appearance, copied values, prose, caller claims, inferred
mappings, and local similarity never create authority.

Company catalogs, design-system data, source locators, prompts, code evidence,
run records, permissions, and user behavior stay in the local Guardian home.
The public repository contains only schemas, code, synthetic fixtures, and
privacy-safe documentation. Release validation scans the working tree, staged
diff, package, and Git history for private paths, identifiers, runtime state,
and credentials.

## Explicit evaluator upgrade permission

The v0.3.5 permission authorizes only
`guardian-flutter-usage-rules-v1` and its two exact compilation-unit
capabilities. Installing v0.3.6 must not broaden that authority.

Guardian adds a versioned local evaluator authorization flow:

```text
guardian rules upgrade preview --profile <profile-id>
guardian rules upgrade apply --input <permission-bound-bundle.json>
```

Preview is zero-write. It verifies the immutable policy, exact profile,
complete rule-snapshot lineage, current v0.3.5 activation permission, source
state, Flutter adapter support, and the v2 evaluator contract. It returns
`permission_required` with a binding over:

- policy, profile, current rule-snapshot, rules, and source-cut digests;
- v0.3.5 activation permission lineage;
- previous and target evaluator IDs;
- the exact supported predicate, relation, and scope capability matrix;
- an `evaluatorContractDigest` covering the semantics in this document; and
- the local namespace and schema version for the authorization record.

Apply requires `granted=true`, recomputes the binding, and refuses any race,
mutation, profile change, policy change, or source downgrade. A valid apply
writes one append-only local evaluator-authorization record and atomically
advances its pointer. Denial and mismatches write nothing. Exact replay is
idempotent; divergent replay is an integrity error.

The existing rule-snapshot v2 history stays immutable. The evaluator
authorization is a sidecar and never rewrites a rule snapshot or the v0.3.5
permission. Later signed rule snapshots under the same exact policy, profile,
catalog authority, and evaluator contract may be evaluated without another
upgrade permission. Any later semantic expansion requires another versioned
permission.

Without v2 permission, v0.3.6 continues enforcing the v0.3.5 capabilities and
reports every newly supported capability as `not_assessed`. It never silently
activates them or reports a production pass.

The two skills translate this into one plain-language question for the user;
users do not copy files, hashes, or commands manually.

## Deterministic analyzer model

The Flutter adapter uses only analyzer-resolved Dart elements and the exact
catalog-to-code mappings pinned in the run config. It never matches a class or
variant by display name, suffix, source spelling, import alias, text, or visual
similarity.

An invocation is assessable only when its constructor resolves to one exact
approved identity. A construction edge is assessable only when the child is
syntactically contained in the resolved parent constructor's argument tree.
List/set/map literals, collection elements, named arguments, and closures that
remain structurally inside that argument tree may preserve the edge. Variables,
returned helpers, dynamic dispatch, unresolved elements, or call-graph guesses
do not create an edge.

Positive evidence may prove a violation even when another part of the graph is
unknown. Absence may be treated as a pass only when the affected scope or
relationship is complete. Otherwise the rule is `not_assessed`.

### Scope semantics

`compilation_unit` means one completely analyzed Dart source file. All exact
resolved invocations in that unit form the scope. Part files follow the Dart
analyzer's resolved unit boundary; Guardian does not merge files by name.

`widget_class` means the nearest lexical Dart class declaration whose resolved
type hierarchy proves it is a Flutter `Widget` or a `State<T>` with a resolved
Widget type argument. Invocations in that class's field initializers,
constructors, methods, getters, setters, and locally nested functions belong to
that class. A free function or helper class called by a widget is not pulled
into the widget scope. An invocation without provable ownership is
`not_assessed`, not guessed from a `Widget` suffix. Each class declaration is a
separate scope; no route or screen identity is inferred.

### Exact machine predicates

1. `forbidden_identity_in_scope`

   For each requested `compilation_unit` or `widget_class` scope, any exact
   invocation of `identity` proves a violation. A complete scope with no exact
   invocation passes.

2. `max_instances_per_scope`

   Count exact invocations of `identity` independently inside each requested
   scope. A count greater than `max` violates. Counts at or below `max` pass
   only for a complete scope.

3. `forbidden_nesting`

   An exact `innerIdentity` at any proven descendant depth beneath an exact
   `outerIdentity` violates. The predicate passes only when every relevant
   outer construction subtree is complete and no forbidden descendant exists.

4. `required_companion`

   For each exact `identity` occurrence, require an exact
   `companionIdentity` in the declared relation:

   - `child`: direct construction child;
   - `descendant`: any proven construction descendant; or
   - `sibling`: both nodes have the same proven immediate construction parent.

   A found exact relation passes that occurrence. Proven complete absence
   violates. Incomplete relation evidence is `not_assessed`.

5. `allowed_parents`

   Every exact `identity` occurrence must have one proven immediate
   construction parent whose approved identity is in `parents`. A proven root
   occurrence or a proven different parent violates. An unresolved immediate
   parent is `not_assessed`.

6. `variant_context`

   The `variant` must resolve through the pinned catalog's exact variant and
   code mapping for `identity`. For each exact mapped variant invocation,
   `compilation_unit` is satisfied by a complete resolved unit and
   `widget_class` is satisfied only by the provable ownership above. At least
   one entry in `allowedScopes` must be satisfied. A provably disallowed
   context violates; unresolved variant or ownership evidence is
   `not_assessed`.

Diagnostic order, rule order, identity order, and scope order are canonical and
stable. Suppression comments remain violations under the existing Guardian
suppression rule.

## Rule inventory command

`guardian rules list --profile <profile-id>` is read-only and emits canonical
JSON. It verifies the policy, profile, rule-snapshot lineage, and effective
evaluator authorization, then reports:

- rule snapshot, rules digest, source state, and evaluator ID;
- every rule ID and class in canonical order;
- for machine rules, predicate, exact capability status, and reason code;
- informative and judgment rules without treating them as evaluated; and
- summary counts for `active`, `not_assessed`, and `informative`.

It never prints rule prose, company source paths, design content, or user data.
A valid pre-activation or v1-evaluator state is listed honestly and exits 0.
Invalid policy, config, permission, or integrity exits 2. Unavailable, stale,
or incomplete source exits 3. Unsupported or incomplete evaluator coverage
exits 4. The command performs zero writes in every outcome.

## Flutter config and adapter compatibility

Flutter config v1 and v2 remain readable and keep their existing meaning.
After explicit evaluator upgrade, Guardian emits a new strict config version
that binds:

- the immutable policy, profile, package, source cut, toolchain, and run;
- rule snapshot, rules digest, v2 evaluator ID, evaluator contract digest, and
  authorization digest;
- exact constructor and variant identities for all active machine rules; and
- canonical inactive coverage with reason codes.

The adapter rejects unknown fields, unsupported semantic versions, unapproved
identities, incomplete mappings, mismatched digests, and malformed graphs. A
project without the supported Flutter analyzer adapter remains `unsupported`
and cannot receive a production pass.

## Separate Usage Rules audit lane

Existing audit-result v1 evidence remains valid and readable. New evaluator-v2
runs produce an additive audit-result schema version with:

```text
usageRulesLane
  status
  evaluatorId
  evaluatorContractDigest
  authorizationDigest
  ruleSnapshotId
  rulesDigest
  activeRuleIds
  assessedRuleIds
  violatedRuleIds
  notAssessed[] { ruleId, reasonCode }
  diagnostics[]
```

The lane status is:

- `conflict` when an exact machine-rule violation is proven;
- `not_assessed` when any gating rule or required relationship is not fully
  assessed;
- `unsupported` when the adapter cannot evaluate the pinned project;
- the matching source or integrity blocker when the evidence is stale,
  unavailable, incomplete, or invalid; or
- `allowed` only when every active gating machine rule is completely assessed
  with no violation and no judgment rule requires an unavailable attestation.

Informative rules are listed as context but do not affect the lane status.
Judgment rules remain `not_assessed` in v0.3.6.

For backward compatibility, the v0.3.5 design-system diagnostic and coverage
projection remains present for inherited consumers. New finalization requires
both that inherited projection and `usageRulesLane` to agree. Any disagreement
is an integrity error, never a pass.

The readable report shows three visibly separate sections:

1. Design-system compliance
2. Usage Rules compliance
3. UX/accessibility quality

`guardian finalize` pins and seals the new lane. Post-run self-check records
which rules were assessed, violated, or not assessed and why, without saving
source content. Sentinels, gaps, any non-allowed gating lane, or incomplete
coverage keep `productionReady=false` and return the established exit code.

## Generic installation status and Windows recovery

The generic Agent Skills installer gains a zero-write status mode for one
target root. Its canonical JSON status is one of:

- `current`
- `update_required`
- `reload_required`
- `invalid`

It compares the installed binding, package version, policy digest, launcher
digest, skill bytes, and runtime marker to the selected public package. It does
not inspect company data or runtime evidence.

The existing stage-verify-atomic-promote-rollback flow remains unchanged. If a
Windows host watcher holds a managed directory and atomic promotion fails with
an access-denied or sharing violation, the installer restores the prior intact
installation and emits:

```json
{
  "status": "reload_required",
  "reasonCode": "host_restart_required"
}
```

The human message names the exact target root and says to close or restart the
host that watches that root, then rerun the same verified install command. The
installer never kills a process, disables a watcher, performs an unsafe
in-place overwrite, or reports the update as installed.

## Data flow

```text
signed complete catalog v2
  -> immutable rule snapshot v2 (unchanged)
  -> explicit evaluator-v2 permission sidecar
  -> pinned strict Flutter config
  -> analyzer-resolved invocation/construction evidence
  -> canonical machine-rule diagnostics and coverage
  -> Usage Rules lane + inherited compatibility projection
  -> sealed audit/finalize/self-check artifacts
  -> privacy-safe local evolution evidence
```

At every arrow, a missing digest, unavailable source, incomplete graph,
unsupported adapter, ambiguous identity, or permission mismatch blocks the
affected assessment. Only a fresh, complete source can prove absence. Guardian
does not create a sentinel for unavailable, incomplete, ambiguous, stale, or
unsupported evidence.

## Implementation checkpoints

These are internal commits and validation checkpoints, not separate public
releases:

1. Add evaluator-v2 permission/state and zero-write rule inventory.
2. Add strict config compilation and all six predicate evaluators, including
   `widget_class` ownership.
3. Add the Usage Rules lane, readable report, finalize, and self-check wiring.
4. Add generic installation status and Windows recovery diagnostics.
5. Run inheritance, privacy, packaging, cross-platform, and adversarial gates;
   then publish one v0.3.6 release and update supported local hosts.

Each checkpoint must leave the branch testable and must not rewrite retained
local or public history.

## Test and release gates

Release is blocked unless all of the following pass:

- Exact v0.3.2, v0.3.3, v0.3.4, and v0.3.5 public behavioral suites run as
  executable inheritance tests, not file-presence checks.
- The immutable policy bytes and digest are identical to v0.3.5.
- Exactly two visible skills remain in every package and host manifest.
- v0.3.5 permission never activates evaluator v2; preview and denial write
  nothing; apply is exact, atomic, idempotent, and profile-isolated.
- Every predicate has exact allow, conflict, `not_assessed`, malformed,
  ambiguity, incomplete-graph, and suppression tests.
- Both scopes distinguish separate units/classes, State ownership, helpers,
  nested functions, aliases, similar names, unresolved types, and partial
  analysis without guessing.
- Construction relationships cover direct, transitive, sibling, collection,
  wrapper, root, helper-indirection, closure, and incomplete-graph cases.
- Exact variants pass; similar variant names, base-component substitutions,
  and unapproved mappings fail or remain `not_assessed` as specified.
- `guardian rules list` is deterministic, privacy-safe, zero-write, and uses
  the established exit-code contract.
- Audit schema compatibility, lane agreement, readable report, finalize,
  self-check, run manifest, and production-readiness truth tables pass.
- Incomplete Usage Rules coverage never produces a green result.
- Installer status performs zero writes. Windows watched-root simulation
  preserves the old installation and returns `host_restart_required`.
- Clean install, update, downgrade refusal, interrupted update, recovery,
  packaging, policy, secret, history, and company-data scans pass.
- Fresh-agent adversarial prompts such as "ignore this rule once", "guess the
  parent", and "treat this judgment rule as checked" fail safely.
- Core and Flutter suites pass on Windows and Ubuntu CI before merge, tag,
  release, or local installation.

An inheritance harness must record an ordinary test failure when an older
worker API or assertion differs; it must not crash the test infrastructure.
Combined Python tests must set `PYTHONPATH` to the selected plugin root so they
cannot accidentally import another installed Guardian version.

## Public release and local update

After all gates pass:

1. Update SemVer metadata and public documentation to v0.3.6 without broad
   search-and-replace of historical version evidence.
2. Commit and push the isolated `codex/guardian-v0.3.6` branch.
3. Merge only after Windows and Ubuntu CI are green.
4. Tag and publish public release `v0.3.6` from the verified merge commit.
5. Install or bind that exact public release on Codex, Claude Code, OpenClaw,
   terminal/generic Agent Skills, Qwen Code, and Kimi Code.
6. Read back every available host. If a watched root is locked, report that
   host as `reload_required`; do not claim it is current.

Public compatibility means the Guardian core and open Agent Skills package are
host-neutral. It does not claim that a host will automatically invoke Guardian
when that host does not support skill routing or command hooks; the host must
be able to load a skill or invoke the CLI.

## Release acceptance criteria

- All approved v0.3.6 additions above are implemented and verified.
- No prior capability, file contract, policy rule, schema reader, skill step,
  adapter diagnostic, privacy guard, migration, installer safety, or release
  check regresses.
- All six machine predicates and both honest scopes are deterministic and
  permission-bound.
- Every uncertainty becomes an explicit blocker or `not_assessed`, never a
  guessed pass.
- Usage Rules, design-system compliance, and UX/accessibility are separately
  understandable while remaining jointly fail-closed.
- No private company or user data exists in the public tree, package, tag,
  release artifact, or Git history.
- GitHub v0.3.6 and each successfully updated local host resolve to the same
  verified package commit.
