# Design System Guardian Flutter adapter

This package is the Flutter-first enforcement adapter for Design System Guardian. It uses Dart's supported analyzer-plugin system introduced in Dart 3.10. It is not a legacy analyzer plugin and it does not use `custom_lint`.

The package registers default-on warning rules through a top-level `plugin`, `Plugin.register`, `AnalysisRule`, `SimpleAstVisitor<void>`, and `PluginRegistry.registerWarningRule`. This follows the current [Dart analyzer-plugin guide](https://dart.dev/tools/analyzer-plugins) and the Dart SDK's [rule-authoring contract](https://github.com/dart-lang/sdk/blob/main/pkg/analysis_server_plugin/doc/writing_rules.md).

## Immutable behavior

Only exact code identities generated from resolved analyzer elements can pass. The canonical identity is the resolved library URI plus the resolved element chain, such as:

```text
package:example_company_design_system/example_company_design_system.dart#AppColors.primary
```

Source spelling, import prefixes, equal-looking values, framework defaults, wrappers without an approved mapping, closest colors, substitute icons, and name guesses do not count. An unresolved element has no identity and cannot pass.

For an authorized build, the default adapter config path is:

```text
<project-root>/.design-system-guardian/flutter-adapter.json
```

For a product-read-only audit, generate the config outside the product tree and set `DESIGN_SYSTEM_GUARDIAN_FLUTTER_CONFIG` to that exact path for the analyzer process. The environment variable changes location only; it cannot broaden the allowlist.

The config is generated by Guardian, never hand-authored. It is bound to `profileId`, `policyDigest`, `snapshotId`, `sourceCutDigest`, and `configDigest`. The Dart loader verifies its exact schema and canonical SHA-256 digest. The host-owned Python audit runner regenerates the complete config from the pinned signed snapshot. Missing, malformed, hand-broadened, cross-profile, cross-snapshot, or altered evidence fails closed and cannot enter the audit lane.

## Governed package provenance

The generated `approvedPackages` object binds every approved package name to an exact `contentDigest` and full 40- or 64-character lowercase `repositoryCommit`. All signed Flutter mappings from one package must carry the same `sourceDigest`; variants must stay in the component package. For Flutter mappings, `sourceDigest` normatively means the SHA-256 of this canonical JSON object:

```json
{"algorithm":"design-system-guardian.flutter-package-content.v1","files":[{"path":"<sorted package-relative path>","sha256":"<file digest>"}],"schemaVersion":1}
```

The `files` array contains every regular file in one clean immutable package artifact, sorted by path. Links, reparse points, case-colliding paths, non-regular files, and cache or excluded directories such as `.dart_tool`, `.git`, `build`, and `coverage` are rejected; they are never silently omitted from the digest.

Before analysis, the trusted runner always parses package-config version 2, even when there are no catalog-approved design-system packages. The profile-owned `requiredPackages` map must include exact `flutter` authority and may bind other semantic dependencies. Every package-config entry other than the analyzed product must appear exactly once in either `requiredPackages` or catalog-derived `approvedPackages`; those namespaces must be disjoint. Guardian rejects duplicate names or roots, redirects, unexpected packages, non-`lib/` package URIs, and content or `pubspec.yaml` identity mismatches. It copies every governed package into host-owned staging and seals and rechecks the originals during analysis and finalization.

The sealed scope is `complete_package_config_closure`: it covers the product's complete Dart package-config closure. It does not claim native libraries, build-tool plugins, SDK-host dependencies, or artifacts outside package-config. Required framework/dependency packages are execution semantics only and can never become approved visual identities.

The selected profile also binds a full Dart SDK artifact per supported platform: exact platform ID, executable-relative identity, and complete content digest. `PATH` is discovery only. Guardian verifies the entire SDK and its unredirected path chain before executing anything, copies it into isolated host staging, runs the staged executable with a minimal environment, and rechecks the original SDK during analysis and finalization. A missing, counterfeit, redirected, overlapping, changed, or platform-mismatched SDK is an integrity failure, never a fallback to ambient Dart or Flutter.

## Default-on diagnostics

The plugin registers warnings for:

- invalid or absent config binding;
- raw or unapproved colors and `TextStyle` values;
- framework, generated, substitute, or unapproved icons;
- raw or unapproved spacing, sizes, and radii;
- raw or unapproved effects and motion;
- raw `dart:ui` drawing, custom painters/decorations, Canvas operations, mutable visual setters, and image/font/SVG asset entry points; framework and community primitives remain forbidden even if placed in a mapping;
- unapproved widgets/components and component variants;
- every use of the diagnostic sentinel, which is permitted for build visibility but always fails production readiness; and
- Guardian suppression comments.

Warnings are enabled by default. Disabling a Guardian diagnostic is itself a policy violation. The external suppression scan checks source comments and analysis-options files as a conservative second lane. Regex is not AST proof; its output always says `method=conservative_text_scan` and `astProof=false`. Only the analyzer rules provide `dart_analyzer_ast` evidence.

## Fixed diagnostic sentinel

`GuardianMissingSentinel` is the sole styling exception. It has fixed magenta (`#FF00FF`), cyan (`#00FFFF`), and black (`#000000`) styling and exactly five labels:

- `MISSING ICON`
- `MISSING COLOR`
- `MISSING TEXT STYLE`
- `MISSING COMPONENT`
- `MISSING TOKEN`

Every instance requires `requestId` and `policyDigest`. Its manifest digest is compiled into the widget. `productionReady` and `automaticPromotion` are permanently `false`. Agents must import this implementation; they must never improvise, wrap, recolor, or recreate it.

## Deterministic audit handoff

The raw Flutter result contract is [`contracts/flutter-adapter-result.schema.json`](contracts/flutter-adapter-result.schema.json). Its coverage lanes explicitly include components, icons, colors, typography, spacing, radii, effects, and motion. Diagnostics are sorted by path, position, code, and message.

`guardian audit` does not accept this raw result from the caller. Its host-owned runner:

1. inventories and hashes every relevant Dart source and analyzer-influencing input;
2. generates the exact run-bound config and sentinel expectation evidence;
3. analyzes an external staging copy with the shipped adapter;
4. requires exactly one config-digest attestation for every compilation unit;
5. parses diagnostics and performs the conservative suppression scan itself;
6. rejects source or analyzer-input changes during the run; and
7. seals the complete runner evidence for finalization to recheck.

`tools/guardian_flutter_contract.py normalize` remains an internal contract utility and development aid. Its output alone is never trusted audit evidence.

Invalid evidence exits `2`; violations exit `1`; unsupported or incomplete coverage exits `4`; a clean supported result exits `0`.

## Enable in a Flutter project

Copy the structure from `analysis_options.example.yaml` into the target project's top-level `analysis_options.yaml`, using the installed adapter path. Guardian must generate the bound config before analysis.

## Optional runtime verification commands

These commands are explicit for a machine with Flutter 3.38+/Dart 3.10+. They were not run in this workspace because neither Dart nor Flutter is installed here.

```powershell
flutter pub get
dart analyze --format machine
flutter test
python tools/guardian_flutter_contract.py scan-suppressions --project C:\path\to\app --output suppression-scan.json
python tools/guardian_flutter_contract.py normalize --result flutter-adapter-result.json --config C:\path\to\app\.design-system-guardian\flutter-adapter.json --run-pin run-pin.json --output core-audit-evidence.json
```

For rule-level Dart tests, use the current analyzer test harness documented in the Dart SDK's [testing guide](https://github.com/dart-lang/sdk/blob/main/pkg/analysis_server_plugin/doc/testing_rules.md).

## Compatibility pin

The private pilot pins one tested dependency line instead of accepting analyzer-major drift:

- `analysis_server_plugin 0.3.19`
- `analyzer 14.0.0`
- `analyzer_plugin 0.14.13`
- `analyzer_testing 0.3.3`
- `crypto 3.0.7`

The `analysis_server_plugin 0.3.19` changelog explicitly binds it to analyzer 14.0.0 and analyzer_plugin 0.14.13. A future Guardian release must update and runtime-test the complete set together.
